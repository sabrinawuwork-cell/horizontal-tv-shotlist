# 局部修订与完整编号映射

新稿默认从 A 连续编号，跳过 I/O，临时后缀在首次批准前归一化。已有批准稿的局部反馈则保留原镜号和既有行序；不为插删一个镜头重排无关引用。两者由实际旧稿和修订记录区分，不能只写一句“局部修订”解除检查。

旧稿使用同项目、同集的完整 approved Stage 1 快照；不得把尚未批准的新稿、另一项目、空表或不明编号的片段当作基线。原始基线仍须符合当前规范编号；历史局部版本必须能沿已绑定记录追溯。批准状态表示已有用户确认，生成记录本身不构成批准。

## 有限的两种操作

- `local`：已有镜号保留。每个实际修改、删除、新增都写清具体理由；没有改变的镜头不得冒充修改。新镜使用旧锚点基础字母加正整数后缀，例如在 `1B` 后插入 `1B-1`。锚点必须来自实际旧主序列，可明确放在其前或后；锚点本次被删除也可保留其位置。既有主镜顺序不变，已经使用的插镜 ID 不因后来删掉基础镜而失效。仅换编号不得伪装为删除加新增。
- `renumber`：确有必要时，对完整主序列按行序生成旧→新映射。该次操作只迁移编号，不同时插删镜或改变表演、台词、摄影机与时长；内容改动先在 `local` 中完成。剪辑列的镜号引用、两类镜号授权、既有 COV 表及绑定的连续性记录须按完整映射同步。引号内原文保留，不做全局文本替换。

纯重编号不改变剧本、场景图、前置导演方案及其他已绑定创作输入的摘要。已具备逐镜发声定位的对白记录只按完整映射更新镜号键，原文、来源定位和发声选择不变；历史旧格式的重编号仍要求对白文件逐字节不变。它不自动改写任意历史文件或自由文字。主序列与 COV 的动作正文、台词和摄影机不允许因为文本像镜号就被替换；确有其他混合修订先单独完成并复核。独立的外部剪辑项目、文件名和未声明自由文字引用仍须按映射人工核对，当前工具不认证这些外部文件已同步。

## 实际文件协议

本节记录已完成的内容修订，不负责替导演决定改什么。实际改稿先回到[导演核心的分类与修订处理](director-core.md#复核与局部修订)：设计变更重推受影响的完整镜头事件，表达问题依据已定拍法纠正，下游遗漏在丢失处修，评审误判不改作品。机位/走位已变但旧左右、裁切或可见面仍被照抄，即使新旧映射和摘要正确也未完成修订；内容稳定后再生成以下记录。

新 Stage 1 增加成对字段：

```yaml
revision_record: revisions/revision-v002.json
revision_record_sha256: <该文件真实SHA-256>
```

记录只使用以下字段：

```json
{
  "version": 1,
  "mode": "local",
  "reason": "按本次反馈补入必要反应，保留其他镜号",
  "base_stage1": "../stage1-v001.md",
  "base_stage1_sha256": "<实际旧稿摘要>",
  "changes": [
    {"kind":"modify", "shot":"1B", "reason":"调整接到反应前的切点"},
    {"kind":"insert", "shot":"1B-1", "anchor":"1B", "position":"after", "reason":"补足本场必要反应"}
  ],
  "mapping": ["由实际旧新七列行生成的完整对象数组，见下方工具"]
}
```

删除项使用 `{"kind":"delete","shot":"1C","reason":"明确删除理由"}`。`renumber` 的 `changes` 固定为空数组，`reason` 说明确需重编的原因。`mapping` 覆盖全部主镜而非只有改动镜：每项记录 `old`、`new`、旧新一基行序 `old_index/new_index` 和两方真实七列单元格数组的 `old_row_sha256/new_row_sha256`。新增的旧侧、删除的新侧为 `null`；删除项按旧行序列在新主序列之后。重编按实际旧新行序一一配对。

先保存旧稿和必要的旧连续性记录副本，再修新稿。不要覆盖用于映射的历史文件。准备实际变更数组后生成记录：

```sh
python3 scripts/shot_revision.py --base stage1-v001.md --current stage1-v002.md \
  --mode local --reason "按反馈补充必要反应" --changes changes-v002.json \
  --output revisions/revision-v002.json
```

父目录须已存在，工具只新建记录、不覆盖既有记录，也不改旧新稿。将输出的两个字段写入新 Stage 1，再运行完整 `validate_v2_shotlist.py`；新修订稿仍先为 draft，在已有批准范围内确认后才进入后阶段。记录不包含新 Stage 1 文件摘要，避免与 Stage 1 引用记录形成循环；真实行摘要会检测未声明的内容变化。

纯重编使用 `--mode renumber`，不传 `--changes`。须先在新稿中同步结构化授权、COV 和连续性记录；生成记录后仍须完整 V2 校验，不能只凭映射生成成功交付。

## 下游与验证边界

Stage 2 和 Stage 3 绑定当前 Stage 1 的实际文件及摘要。Stage 3 镜号全集和顺序必须与通过验证的 Stage 1 相同，不能自行声明编号例外。固定卡、编译记录、生成任务使用新 ID；旧绑定会失败，不能只给 Stage 3 改一列掩盖旧来源。

任务导出的 `edit-map.json` 和原表更新预览附带当前 `shot_revision` 完整映射。新旧稿、修订记录及实际用到的历史编号链都会进入输入快照；纯重编额外保护用于核对的旧连续性记录和旧对白记录。历史节点与当前制作来源分别标明用途，不读取已不再使用的旧剧本、旧场景资产或整个项目历史。

原工作簿更新同时核对目标旧镜号与实际映射：不能用插镜覆盖目标区仍保留的旧镜，也不能将其他旧镜误塞进当前区。插镜需要明确授权的现有空位；删除需明确清理旧尾，不能擅自挪动保护区或物理插删 Excel 行。当前带修订记录的原表更新只对主序列做此映射核对，覆盖表需独立核对，不能冒用主镜映射更新。

文件变化或改后还原会使旧任务导出或工作簿预览失效。结构检查只证明实际声明、行序和来源对应；不证明修订理由已获授权、设计合理、场面成立或未声明外部引用已经更新。

## 旧对白记录接入当前制作

迁移只处理本次实际使用的稿件。旧批准Stage1、它引用的对白记录及历史修订链保持原样，不为补字段重写旧文件或重算旧摘要。历史纯重编号若使用同一份字节未变的旧对白清单，可继续作为编号来源；这只认可历史编号关系，不把缺定位的旧清单当成已完成新版对白核对。

代理先另存正文、镜号和行序不变的当前Stage1制作副本，再新建对白记录：保留旧清单的`dialogue`原文与既有来源范围，依据同一权威剧本和实际镜头补齐缺少的来源及逐镜发声定位。完整性、说话者和真实发声仍须对源核对，不能仅把格式转换成功当作内容通过。新副本引用新记录及其摘要，旧原件不动。

采用现有`local`修订记录引用实际旧Stage1，`reason`说明仅补内部定位；七列内容与镜号没有变化时`changes`用空数组，不虚构修改镜头。内容批准沿用已经确认的范围，仅补内部记录不增加用户审批；若核对发现原文或导演决定确需改变，则按原有内容修订和批准边界处理。以后确需`renumber`时，以这个已核实的制作副本为基线，按正常映射同步新的对白记录。不得把旧格式迁移与重编号揉进一次操作，迫使旧批准文件改写。

Stage2/3及任务绑定只沿当前制作副本更新；历史交付仍保留旧引用，不批量改写为新版结果。用户不填迁移表，代理使用现有记录和修订工具完成衔接，不另加迁移工具或阶段。

## 同一轮修订的收束

先合并本轮已决定的导演/镜头改动并完成内容复核，正文稳定后再生成该版本的完整修订映射、同步下游绑定和导出交付。探索中的逐句改写不必每次都重建完整任务和工作簿；已有受影响交付在重导出前须明确失效。真正新增的修改仍须重新核对与传播，不能靠复用旧摘要跳过。

重编号时，代理将既有对白记录的`stage1_speech`键按完整镜号映射同步，原文数组、原剧本定位和各镜发声选择保持不变。旧稿引用的对白记录另存保留，新稿引用新的记录与摘要；不得为同步镜号覆盖旧记录或顺带改台词。程序比较实际旧新记录，导出同时保护两份记录的读取快照。
